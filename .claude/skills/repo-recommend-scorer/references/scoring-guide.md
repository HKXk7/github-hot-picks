# 打分细则参考

这份是打分时的补充说明，SKILL.md 里没展开的细节都在这里。

## 一个完整的打分示例

假设本周抓到 3 个候选，用默认权重演示打分过程：

### 候选 A：某个「小而美」的新工具
- stars 3200，本周 +1800，创建于 2 个月前，MIT，有中文 README
- 成长性：+1800 → 落在 500–2000 → **24**
- 新鲜度：2 个月 → **20**
- 稀缺性：3200 < 5k 且上升中 → **20**
- 上手友好：有中文 README → **15**
- 许可证：MIT → **15**
- 总分 **94** → 强力推荐，理由聚焦「新 + 涨得快 + 有中文文档」

### 候选 B：人人皆知的大热门
- stars 180k，本周 +3000，创建 6 年，MIT
- 成长性：+3000 ≥ 2000 → 30
- 新鲜度：6 年 → 4
- 稀缺性：家喻户晓 → **0**
- 上手友好：英文但文档极好 → 9
- 许可证：15
- 总分 **58** → 不推。虽然涨得猛，但「人人皆知」把分数压下来了，这正是稀缺性维度的意义。

### 候选 C：文档缺失的冷门库
- stars 900，本周 +40，创建 8 个月，无许可证，README 只有两行
- 成长性：40 → 8
- 新鲜度：8 个月 → 14
- 稀缺性：900 < 5k → 20
- 上手友好：文档缺失 → 4
- 许可证：无 → 2
- 总分 **48** → 不推。冷门但「无许可证 + 没文档」双重劝退，新手用不了。

结论：只推 A。

## 许可证友好度清单

- **随便用（满分档）**：MIT、Apache-2.0、BSD-2-Clause、BSD-3-Clause、ISC、Unlicense、CC0-1.0
- **基本能用（中档）**：MPL-2.0（文件级 copyleft）、LGPL（链接不受限）、WTFPL
- **商用要小心（低档）**：GPL-2.0/3.0（衍生作品必须开源）、AGPL-3.0（联网服务也传染）
- **不能拿来商用（最低档）**：CC BY-NC 等非商用协议
- **没有许可证（最低档）**：`license: null` —— 法律上默认「保留所有权利」，别人不能合法复用

判断优先级：以 GitHub API 返回的 `license.spdx_id` 为准；没有就按 `none`。

## 新手最容易误判的几个点

1. **star 多 ≠ 值得推荐**。稀缺性维度专门压这个。180k star 的 vue 再好，读者也不需要你推荐。
2. **涨得快的老项目也别急着推**。成长性满分（+3000）但新鲜度 4 分、稀缺度 0 分的，总分照样不达标。
3. **数据缺失给中性分，不是零分**。新库 star 少很正常，别把「本周 +0」误读成「烂项目」。
4. **许可证别凭印象**。看到「Apache」默认宽松是对的，但看到「GPL」要警觉，看到「CC」要看清后缀是不是 NC。
5. **去重优先于打分**。已经推过的，再高分也默认不进新榜单，否则读者会觉得你在炒冷饭。

## 历史记录文件格式约定

`data/recommended.json` 长这样：

```json
[
  { "full_name": "owner/repo", "recommended_at": "2026-10-20" },
  { "full_name": "owner/another", "recommended_at": "2026-10-13" }
]
```

去重只看 `full_name`。每次推荐完记得把新项目追加进去，这样下周自动跳过。
