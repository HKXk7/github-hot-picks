# 给 GitHub 候选项目筛选打分

## 这个 skill 是干什么的

它在整条周报流水线里负责**信息筛选**这一环（最值钱的一环）：

```
抓数据(github-trending-fetch) → 筛选打分(本 skill) → 写稿(weekly-repo-digest)
```

输入是一批候选仓库的元数据（JSON 数组），输出是**排好序的 Top N + 每条一句推荐理由**。
目的：把「这周选哪几个项目」这个靠人肉纠结的活儿，变成一套可复用、可调权重的打分规则。

## 输入约定

每个候选仓库至少要有这些字段（来自 github-trending-fetch，字段名以它为准）：

| 字段 | 含义 | 缺失时怎么办 |
| --- | --- | --- |
| full_name | 仓库全名 owner/repo | 缺则跳过 |
| stars / stargazers_count | 总 star | 缺则成长性用中性分 |
| stars_this_week | 本周新增 star | 缺则成长性用中性分 |
| created_at | 创建时间 | 缺则新鲜度用中性分 |
| language | 主要语言 | 缺则留空，不影响打分 |
| description | 描述 | 缺则上手友好降一档 |
| topics | 标签 | 辅助判断用途 |
| license | 许可证 SPDX 标识或 null | 缺则按「无许可证」计 |
| is_archived / archived | 是否已归档 | 归档直接排除 |
| is_fork / fork | 是否 fork | fork 一般排除 |

## 打分流程（五步）

1. **读配置**：先读 `resources/scoring-rules.json`，拿到当前权重和阈值。
   **要调权重只改这个 json，不要改本文件。**
2. **硬性过滤**：先剔除不该进榜单的——已归档、纯 fork、已推荐过（见「去重规则」）。
3. **逐维打分**：对每个候选按下面五个维度打分，各维度得分上限 = 该维度权重。
4. **求和排序**：总分 0–100，从高到低排。
5. **写理由**：给 Top N 各写一句话推荐理由，再按「输出格式」交付。

## 五个维度与判定标准

总分 = 成长性 + 新鲜度 + 稀缺性 + 上手友好 + 许可证（满分 100）。
各维度满分为 `scoring-rules.json` 里的权重值，下面的数字是默认权重下的参考分。

### ① 成长性 growth（满分 30）—— 本周涨得多快

按 `stars_this_week`：

| 本周新增 star | 得分 |
| --- | --- |
| ≥ 2000 | 30 |
| 500–2000 | 24 |
| 100–500 | 15 |
| 30–100 | 8 |
| < 30 | 3 |
| 缺失 | 6（中性） |

### ② 新鲜度 freshness（满分 20）—— 是不是刚冒出来的

按「当前日期 - created_at」：

| 创建至今 | 得分 |
| --- | --- |
| ≤ 3 个月 | 20 |
| 3–12 个月 | 14 |
| 1–3 年 | 8 |
| > 3 年 | 4 |
| 缺失 | 10（中性） |

### ③ 稀缺性 novelty（满分 20）—— 是不是「小而美」，还是人人皆知

这是推荐稿的**辨识度来源**。推荐「大家还没发现但很好用」的项目，而不是再炒一遍 vue/react。

| 总 star | 得分 |
| --- | --- |
| < 5k 且上升中 | 20（最理想的推荐对象） |
| 5k–20k | 14 |
| 20k–50k | 8 |
| > 50k，或圈内家喻户晓（vue/react/axios/next.js 这类） | 0（降权，不值得浪费推荐位） |

「家喻户晓」判断：如果随便一个同行都听说过，就按 0 算，不要心软。

### ④ 上手友好 accessibility（满分 15）—— 中文读者能不能快速看懂

| 情况 | 得分 |
| --- | --- |
| 有中文 README 或中文文档站 | 15 |
| 纯英文，但文档清晰、有 demo/快速开始 | 9 |
| 文档缺失或只有裸代码 | 4 |

面向中文读者的推荐稿，中文文档是实打实的加分项。

### ⑤ 许可证 license（满分 15）—— 别人能不能放心拿来用

| 情况 | 得分 |
| --- | --- |
| 宽松协议：MIT / Apache-2.0 / BSD-2/3-Clause / ISC / Unlicense | 15 |
| 弱 copyleft：MPL-2.0 / LGPL | 10 |
| 强 copyleft：GPL-2.0 / GPL-3.0 / AGPL | 7 |
| 无许可证（license = null） | 2 |
| 非商用：CC BY-NC 等 | 1 |

完整对照见 `references/scoring-guide.md` 的许可证清单。

## 去重规则（硬性）

- 历史推荐记录文件：`data/recommended.json`（项目内，数组，元素含 `full_name` 和推荐日期）。
- 文件不存在 → 跳过去重，但要提醒用户「还没有历史记录，建议下次开始记录」。
- 命中 `full_name` → **默认排除**（policy=exclude）。除非用户明确要「回顾/复盘」，才标记为「已推荐」但不计入新榜单。

## 输出格式

先给结论表，再给理由。默认 N=5，用户可指定。

```markdown
## 本周推荐 Top 5

| 排名 | 项目 | 语言 | 总分 | 本周 +star | 一句话推荐 |
| --- | --- | --- | --- | --- | --- |
| 1 | owner/repo | TypeScript | 86 | +1200 | 一句话说清它解决什么痛点、为什么这周值得关注 |

### 为什么是这 5 个
1. **owner/repo（86 分）**：理由……
2. ...
```

一句话理由的写法：**「它解决什么痛点 + 为什么现在值得关注」**，结合该项目的最高分维度，别写空话（「很火」「不错」都不算理由）。

## 边界情况（新手最容易踩）

- **候选不足 N 个**：有几个推几个，不凑数，并说明「本周符合条件的只有 X 个」。
- **star 为 0 或新库数据不齐**：成长性给中性分，靠新鲜度 + 稀缺性补，别直接判死刑。
- **fork 仓库**：默认排除（除非用户点名要看某个 fork）。
- **archived 仓库**：直接排除。
- **长期没 commit**（最近提交 > 1 年前）：降权，在理由里注明「维护不活跃」。
- **同分并列**：稀缺性高者优先（更符合「小而美」定位），再比本周新增 star。

## 调参提示

想改口味（比如「更看重中文文档」）→ 只改 `resources/scoring-rules.json` 的 `weights`，
把 `accessibility` 从 15 调到 20，别的维度减 5，总和保持 100 即可。不用动本文件。
